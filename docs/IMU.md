# 🧭 ระบบ IMU (BNO085) — คู่มือฉบับเต็ม

เอกสารนี้อธิบายทุกอย่างเกี่ยวกับ IMU ในโปรเจกต์นี้ ตั้งแต่ตัวเซนเซอร์บนบอร์ด Master
ไปจนถึงการเอาค่ามุมไปใช้หมุนล้อ Mecanum ที่บอร์ด Wheel

> **สรุปสั้นๆ:** IMU ทำให้หุ่น "รู้ว่าตัวเองหันไปทางไหน" ซึ่งตอนนี้เอาไปใช้อย่างเดียวคือ
> **Heading Assist** — ตัวช่วยกันหุ่นเบี้ยวตอนวิ่งตรง
>
> ⚠️ เดิมเคยมี **Field-Oriented Control** ด้วย แต่**ถูกถอดออกแล้ว** เพราะคนบังคับไม่ถนัด
> ตอนนี้จอยเป็น **Robot-Oriented (Local Frame)** ล้วนๆ — ดันจอยขึ้น = หุ่นวิ่งไปทางหน้าของตัวหุ่น
> ดูเหตุผลที่[หัวข้อ 7](#7-เรื่อง-field-oriented-control-ถอดออกแล้ว)

## 1. ฮาร์ดแวร์และการต่อสาย

| รายการ | ค่า |
|---|---|
| เซนเซอร์ | **BNO085** (ตระกูล BNO08x, 9-DOF) |
| บอร์ดที่ต่อ | **0_master** (ESP32-WROOM-32) เท่านั้น |
| การเชื่อมต่อ | I2C |
| SDA | GPIO **21** |
| SCL | GPIO **22** |
| ความเร็ว I2C | 400 kHz |
| I2C Address | **0x4A** (ค่าปกติ) หรือ **0x4B** (ถ้าขา ADR ถูกดึงขึ้น) |
| ไลบรารี | `adafruit/Adafruit BNO08x` |
| อัตรารายงาน | **30 Hz** (ทุก ~33 ms) |

โค้ดจะลองหาที่ `0x4A` ก่อน ถ้าไม่เจอค่อยลอง `0x4B` ให้อัตโนมัติ — ไม่ต้องตั้งอะไรเพิ่ม

### ⚠️ การติดตั้งเชิงกล (สำคัญมาก)

**BNO085 ต้องวางราบขนานกับพื้น** โดยให้แกน Z ชี้ขึ้นฟ้า

เพราะสูตรคำนวณ yaw ในโค้ดคิดว่าการหมุนซ้าย-ขวาของหุ่นคือการหมุนรอบแกน Z
ถ้าเอาไปติดตั้งตะแคงหรือคว่ำ ค่า yaw ที่ได้จะไม่ใช่ทิศที่หุ่นหันจริง และระบบทั้งหมดจะเพี้ยน

**ถ้าติดกลับหัว (คว่ำ)** เครื่องหมายของ yaw จะกลับด้าน ซึ่งอันตรายมาก เพราะ Heading Assist
จะดันหุ่นไป**ผิดทาง** กลายเป็น positive feedback แล้วหุ่นจะหมุนติ้วเอง
👉 ต้องเช็คด้วย [Checklist ข้อ 2](#11-checklist-ทดสอบก่อนลงสนาม) ก่อนขับทุกครั้งที่ย้ายตำแหน่งเซนเซอร์

## 3. ขั้นที่ 1 — อ่านค่าจาก BNO085

📄 `src/0_master/main.cpp` → `beginGyro()` และ `readGyro()`

### 3.1 ทำไมใช้ Game Rotation Vector

BNO085 มีโหมดรายงานหลายแบบ โค้ดนี้เลือกใช้ **`SH2_GAME_ROTATION_VECTOR`**

| โหมด | ใช้เข็มทิศ (Magnetometer) | ข้อดี | ข้อเสีย |
|---|---|---|---|
| `ROTATION_VECTOR` | ใช้ | รู้ทิศเหนือจริง ไม่ดริฟต์ | **โดนมอเตอร์กับเหล็กรบกวนหนัก** |
| `GAME_ROTATION_VECTOR` | **ไม่ใช้** | นิ่ง ไม่โดนมอเตอร์กวน | ดริฟต์ช้าๆ ไม่รู้ทิศเหนือ |

หุ่นเรามีมอเตอร์ BTS7960 กินกระแสสูง 7 ตัว + โครงเหล็ก → สนามแม่เหล็กรอบตัวมั่วมาก
ถ้าใช้เข็มทิศค่าจะเหวี่ยงจนใช้งานไม่ได้เลย **เลยต้องใช้ Game Rotation Vector**

แลกกับการที่ yaw จะ **ดริฟต์ช้าๆ** (ประมาณไม่กี่องศาต่อนาที) และเลข 0 องศาไม่ได้แปลว่าทิศเหนือ
แต่แปลว่า "ทิศที่เรารีเซ็ตไว้ล่าสุด" ซึ่งเหมาะกับการใช้งานในสนามแข่งมากกว่าอยู่แล้ว

### 3.2 Quaternion คืออะไร

เซนเซอร์ไม่ได้ส่งมุมองศามาตรงๆ แต่ส่ง **quaternion** = ตัวเลข 4 ตัว `(qr, qi, qj, qk)`
ที่บอกการหมุนในสามมิติ

ข้อดีของ quaternion คือ**ไม่มีปัญหา Gimbal Lock** (อาการมุมพังตอนเงยหน้า 90°)
แต่คนอ่านไม่รู้เรื่อง เลยต้องแปลงเป็นมุม Euler (roll / pitch / yaw) ก่อนใช้

```cpp
// roll = เอียงซ้าย-ขวา (หมุนรอบแกนหน้า-หลัง)
rollRad = atan2f(2*(qr*qi + qj*qk), 1 - 2*(qi*qi + qj*qj));

// pitch = ก้ม-เงย (หมุนรอบแกนซ้าย-ขวา)
sinPitch = constrain(2*(qr*qj - qk*qi), -1, 1);   // constrain กัน asin พังจากค่าเกิน ±1
pitchRad = asinf(sinPitch);

// yaw = หันซ้าย-ขวา (หมุนรอบแกนตั้ง) <-- ตัวที่เราใช้จริง
yawRad = atan2f(2*(qr*qk + qi*qj), 1 - 2*(qj*qj + qk*qk));
```

โปรเจกต์นี้**ใช้แค่ `yaw`** ส่วน roll/pitch คำนวณไว้เฉยๆ สำหรับ debug (เผื่ออยากรู้ว่าหุ่นเอียง/กระดกไหม)

### 3.3 ทำไมต้อง `constrain(sinPitch, -1, 1)`

`asinf()` รับค่าได้แค่ช่วง −1 ถึง 1 แต่การคำนวณทศนิยมอาจได้ 1.0000001 เพราะความคลาดเคลื่อน
ถ้าไม่ constrain ก่อน `asinf()` จะคืน **NaN** แล้วค่าจะพังทั้งสาย

### 3.4 การจัดการเซนเซอร์รีเซ็ตตัวเอง

```cpp
if (bno08x.wasReset()) {
    gyroOnline = false;
    enableGyroReport();   // ต้องสั่งเปิดรายงานใหม่ ไม่งั้นเซนเซอร์จะเงียบไปเลย
}
```

BNO085 อาจรีบูตตัวเองได้ถ้าไฟตก (เช่นตอนมอเตอร์กระชากกระแส)
พอรีบูตแล้วมันจะ**ลืมว่าเคยถูกสั่งให้ส่งข้อมูลอะไร** ต้องสั่ง `enableReport()` ใหม่ทุกครั้ง

## 4. ขั้นที่ 2 — Yaw Offset และการรีเซ็ตทิศ

### 4.1 ทำไมต้องมี offset

ค่า yaw ดิบ (`gyroRawYawDeg`) นับ 0 จากตอนที่เซนเซอร์บูต ซึ่งเป็นทิศสุ่มๆ ตามที่วางหุ่นไว้ตอนเปิดเครื่อง

เราอยากให้ **0 องศา = ทิศหน้าสนาม** เลยต้องเก็บ offset ไว้ลบออก

```cpp
gyroYawDeg = normalizeAngleDeg(gyroRawYawDeg - gyroYawOffsetDeg);
```

`resetGyroYaw()` ทำแค่จับค่าดิบ ณ ตอนนั้นมาเก็บเป็น offset → ทิศที่หุ่นหันอยู่ ณ วินาทีนั้นกลายเป็น 0 องศา

### 4.2 วิธีรีเซ็ต

| วิธี | ใช้ตอนไหน |
|---|---|
| พิมพ์ `R` หรือ `r` ที่ Serial Monitor ของ Master | ใช้ตอนอยู่หน้าคอม ตอนทดสอบ |

> ⚠️ **ปุ่ม L3 + R3 บนจอยถูกถอดออกแล้ว** (เดิมกดค้าง 0.5 วิ เพื่อรีเซ็ตทิศ)
> เพราะพอไม่มี Field-Oriented แล้ว ทิศ 0 องศาไม่ได้สำคัญเท่าเดิม —
> Heading Assist ใช้แค่ **ผลต่าง** ของมุม ไม่สนว่า 0 อยู่ตรงไหน จึงไม่ต้องรีเซ็ตก่อนแข่ง

### 4.3 `normalizeAngleDeg()` มีไว้ทำไม

บีบมุมให้อยู่ในช่วง **−180° ถึง +180°** เสมอ

ถ้าไม่บีบ พอหุ่นหมุนไปเรื่อยๆ ตัวเลขจะวิ่งเป็น 350, 400, 720 ... แล้วเวลาเอาไปลบกันจะเพี้ยน

**ตัวอย่างที่พังถ้าไม่ normalize:**
หุ่นอยู่ที่ 179° เป้าหมายคือ −179° (ห่างกันแค่ 2° เท่านั้น)
แต่ลบกันตรงๆ ได้ `−179 − 179 = −358°` → ระบบจะสั่งหุ่นหมุนกลับเกือบรอบ! 😱
พอ normalize แล้วจะได้ `+2°` ซึ่งถูกต้อง

ฟังก์ชันนี้มีอยู่ทั้งฝั่ง Master และฝั่ง Wheel เพราะทั้งสองฝั่งต้องใช้

## 5. ขั้นที่ 3 — ตรวจสุขภาพ gyro

📄 `src/0_master/main.cpp` → `isGyroValid()`

```cpp
bool isGyroValid()
{
  return gyroOnline && ((millis() - lastGyroMs) < GYRO_STALE_MS);
}
```

ต้องผ่าน **2 เงื่อนไขพร้อมกัน**:

| เงื่อนไข | ความหมาย |
|---|---|
| `gyroOnline` | เคยเจอเซนเซอร์และเปิดรายงานสำเร็จ |
| ข้อมูลยังสด (< **200 ms**) | มีข้อมูลใหม่เข้ามาจริง ไม่ได้เงียบไป |

### ทำไม `gyroOnline` อย่างเดียวไม่พอ

เพราะโค้ดตั้ง `gyroOnline = false` **เฉพาะตอนเจอ `wasReset()` เท่านั้น**
ถ้าสาย I2C หลุด/ขาด ตัวแปรนี้จะยัง**ค้างเป็น `true` ตลอดไป** ทั้งที่ไม่มีข้อมูลเข้ามาแล้ว

การเช็คความสดเพิ่มจึงจำเป็น — เซนเซอร์ส่งมา 30 Hz (ทุก 33 ms)
ถ้าเงียบเกิน 200 ms (≈ 6 รอบ) แปลว่ามีปัญหาแน่นอน

### เกิดอะไรขึ้นเมื่อ gyro เสีย

```
gyro เสีย ──> Master ส่ง yaw = 0 และ flag = 0
                      │
                      ▼
          Wheel เห็น flag = 0 ──> ปิด Heading Assist
                      │
                      ▼
              คนขับยังบังคับหุ่นได้ปกติ แค่ไม่มีตัวช่วยกันเบี้ยว
```

**ห้ามใช้ yaw ค้างค่าเดิมเด็ดขาด** เพราะ Heading Assist จะเข้าใจว่าหุ่นเบี้ยวอยู่ตลอดแล้วดันหุ่นผิดทาง

ที่ Serial Monitor ของ Master จะขึ้นข้อความตอนสถานะเปลี่ยน:
```
GYRO OK -> HEADING ASSIST ENABLED
GYRO LOST -> HEADING ASSIST DISABLED
```

## 6. ขั้นที่ 4 — ส่งข้ามบอร์ดผ่าน UART

📄 `lib/Protocol/protocol.h` และ `protocol.cpp`

### 6.1 โครงสร้างข้อมูล

```cpp
struct WheelCommand {
    float vx;      // ความเร็วหน้า-หลัง
    float vy;      // ความเร็วซ้าย-ขวา (สไลด์)
    float omega;   // ความเร็วหมุน
    float yaw;     // <-- มุมจาก IMU (องศา, -180..180)
    uint8_t flags; // <-- bit0 = yaw เชื่อถือได้ไหม
};
```

`flags` ใช้บิตแรกตัวเดียว:
```cpp
#define WHEEL_FLAG_GYRO_VALID 0x01
```

### 6.2 รูปแบบเฟรม

```
┌────────┬────────┬──────────────────────┬──────────┐
│  0xAA  │   20   │   payload 20 ไบต์     │ checksum │
│ start  │  len   │  (WheelCommand)      │   XOR    │
└────────┴────────┴──────────────────────┴──────────┘
        รวม 23 ไบต์ ส่งที่ 50 Hz = 1,150 ไบต์/วินาที
        (ใช้แบนด์วิดท์แค่ ~10% ของ UART 115200)
```

> **หมายเหตุ:** struct มีขนาด **20 ไบต์** ไม่ใช่ 17
> เพราะคอมไพเลอร์เติม padding 3 ไบต์ต่อท้าย `flags` เพื่อจัดตำแหน่งหน่วยความจำให้ลงตัว
> (ยืนยันแล้วว่า ESP32 กับ STM32 เห็นตรงกันทั้งคู่)

### 6.3 ⚠️ ต้องแฟลชพร้อมกัน

`WheelCommand` เคยมีขนาด 16 ไบต์ ตอนนี้เป็น 20 ไบต์
👉 **ต้องแฟลช `0_master` กับ `2_slave_wheel` พร้อมกันเสมอ**

ถ้าแฟลชไม่ครบ ฝั่งรับจะเห็น `len` ไม่ตรงแล้ว**ทิ้งเฟรมทั้งหมด** → ล้อจะ timeout แล้วหยุดนิ่ง
(อาการนี้ปลอดภัย แต่จะงงว่าทำไมหุ่นไม่วิ่ง — ให้นึกถึงข้อนี้ก่อนเลย)

> `1_slave_arm` **ไม่ต้อง**แฟลชใหม่ เพราะไม่ได้ใช้ `WheelCommand`

### 6.4 ถ้าสายขาด

ฝั่ง Wheel มีตัวจับเวลา **`WHEEL_CMD_TIMEOUT_MS = 300 ms`**
ถ้าไม่มีเฟรมเข้ามาเกิน 300 ms จะ:
1. ตั้งความเร็วเป็น 0 ทั้งหมด
2. ตั้ง `g_gyro_valid = false` (เพราะไม่รู้แล้วว่า gyro ฝั่งโน้นยังดีอยู่ไหม)
3. เรียก `stopBase()` ซึ่งล้าง integral ของ PID ทั้ง 4 ตัวด้วย

## 7. เรื่อง Field-Oriented Control (ถอดออกแล้ว)

📄 `src/2_slave_wheel/main.cpp` → `moveBase()`

### 7.1 ตอนนี้เป็นแบบไหน

**Robot-Oriented (Local Frame)** — ดันจอยขึ้น = หุ่นวิ่งไปทาง "หน้าของตัวหุ่น"
ค่าจากจอยส่งเข้า kinematics ตรงๆ ไม่ผ่านการหมุนใดๆ

```cpp
void moveBase()
{
    // Local frame: ส่งค่าจากจอยเข้า kinematics ตรงๆ หน้าหุ่นคือหน้าจอยเสมอ
```

## 8. ขั้นที่ 6 — Heading Assist

📄 `src/2_slave_wheel/main.cpp` → `updateHeadingAssist()`

### 8.1 แก้ปัญหาอะไร

เวลาสั่งหุ่นวิ่งตรง หุ่นจริงมักจะ**เบี้ยว**ทีละนิด เพราะ:
- ล้อ 4 ตัวหมุนไม่เท่ากันเป๊ะ (มอเตอร์ต่างกัน, ยางสึกไม่เท่ากัน)
- พื้นสนามไม่เรียบ
- น้ำหนักหุ่นเทไปข้างใดข้างหนึ่ง
- ชนหรือถูกเบียด

Heading Assist จะจำทิศตอนเริ่มวิ่ง แล้วคอย**เติมแรงบิดเล็กๆ** ให้หุ่นกลับมาตรงทิศเดิมเอง

### 8.2 ลำดับการทำงาน

```
เริ่ม updateHeadingAssist()
   │
   ├─ 1. gyro ใช้ไม่ได้? ──────────────> รีเซ็ต, คืน 0
   │
   ├─ 2. yaw กระโดดเกิน 45° ใน 1 รอบ? ─> รีเซ็ต, คืน 0
   │        (= gyro รีบูต ไม่ใช่หุ่นหมุนจริง)
   │
   ├─ 3. คนขับกดปุ่มเลี้ยว (L1/R1)? ───> รีเซ็ต, คืน 0
   │     หรือไม่ได้สั่งวิ่งเลย?           (คนขับสั่งเอง อย่าไปขัด)
   │
   ├─ 4. เพิ่งเริ่มช่วย? ──> จำ yaw ปัจจุบันเป็นเป้าหมาย
   │
   ├─ 5. error = เป้าหมาย − yaw ปัจจุบัน  (normalize แล้ว)
   │
   ├─ 6. |error| < 1°? ────────────────> ถือว่าตรงแล้ว, คืน 0
   │                                     (กันมอเตอร์กระตุกตลอดเวลา)
   │
   └─ 7. คำนวณ PID ──> trim (RPM ที่จะเติม, จำกัดที่ ±80)
```

### 8.3 เงื่อนไขที่ทำให้ "ปิด" ตัวช่วย

| เงื่อนไข | ทำไม |
|---|---|
| `!g_gyro_valid` | ไม่มี gyro = ไม่รู้ว่าเบี้ยวเท่าไหร่ ห้ามเดา |
| `yaw_step > 45°` ใน 1 รอบ (10 ms) | 45° ใน 10 ms = 4,500°/วินาที ซึ่งหุ่นทำไม่ได้จริง<br>แปลว่า gyro รีบูต/ค่ากระโดด **ห้ามไล่ตาม** |
| `\|omega\| > 0.05` | คนขับกดปุ่มเลี้ยวเอง (L1/R1) ต้องปิดทันที ไม่งั้นจะสู้กัน |
| ไม่ได้สั่งวิ่ง (`vx`, `vy` ต่ำกว่า 0.05) | หุ่นจอดอยู่ ไม่ต้องช่วย |
| `\|error\| < 1°` (deadband) | เบี้ยวนิดเดียว ปล่อยไป ไม่งั้นมอเตอร์จะกระตุกตลอด |

ทุกครั้งที่ปิด จะเรียก `resetHeadingAssist()` ซึ่งล้าง integral ของ PID ด้วย
ถ้าไม่ล้าง ค่าเก่าจะค้างข้ามรอบแล้วดันหุ่นผิดทางตอนเริ่มช่วยรอบใหม่

### 8.4 การเอา trim ไปใช้กับล้อ

```cpp
target_rpm[0] = g_req_rpm.motor1 - trim;  // FL  ซ้ายหน้า
target_rpm[1] = g_req_rpm.motor2 + trim;  // FR  ขวาหน้า
target_rpm[2] = g_req_rpm.motor3 - trim;  // RL  ซ้ายหลัง
target_rpm[3] = g_req_rpm.motor4 + trim;  // RR  ขวาหลัง
```

เครื่องหมาย **−, +, −, +** ตรงกับตำแหน่งของ `tan_rpm` ในสูตร Mecanum พอดี
แปลว่า **trim เป็นบวก = สั่งให้หุ่นบิดทวนเข็มนาฬิกา** (ทิศเดียวกับ omega เป็นบวก)

**ตรวจทิศ:** ถ้าหุ่นเบี้ยวไปทางขวา (ตามเข็ม) → yaw ลดลง → `error = target − yaw` เป็นบวก
→ trim เป็นบวก → หุ่นบิดทวนเข็มกลับมา ✅ ถูกต้อง

> ถ้าเจอว่าหุ่นแก้ไป**ผิดทาง** (ยิ่งเบี้ยวหนัก) ให้เปลี่ยน `HEADING_ASSIST_DIR` จาก `1` เป็น `-1`

### 8.5 ทำไมต้อง `scaleRpmWithinLimit()`

`Kinematics` สเกลค่าให้ไม่เกิน `MAX_RPM` (550) ไปแล้วรอบหนึ่ง
แต่ `trim` ถูกบวกเข้ามา**ทีหลัง** → ล้ออาจถูกสั่งถึง 550 + 80 = **630 RPM** ซึ่งมอเตอร์ทำไม่ได้

ผลเสียถ้าไม่แก้: PID จะสั่ง PWM เต็ม 255 ค้าง → error ไม่ลด → integral สะสม
→ **ตัวช่วยวิ่งตรงถูกกลืนหายไปเฉยๆ ตอนวิ่งเต็มสปีด**

`scaleRpmWithinLimit()` จึงสเกลซ้ำอีกรอบ โดย**สเกลพร้อมกันทั้ง 4 ล้อ**
เพื่อรักษาสัดส่วนเวกเตอร์ไว้ (ห้าม constrain ทีละล้อ เพราะหุ่นจะเบนออกนอกทิศที่สั่ง)

### 9.3 วิธีจูน `HEAD_K_P`

**หน่วยคือ "RPM ที่จะเติมให้ล้อ ต่อ error 1 องศา"**

ที่ค่าปัจจุบัน `0.50` → เบี้ยว 10° จะเติมแรงแค่ 5 RPM (จาก 550) ซึ่ง**ค่อนข้างเบามาก**
เป็นค่าเริ่มต้นที่ปลอดภัย ไม่ทำให้หุ่นส่ายแน่ๆ แต่อาจแก้เบี้ยวได้ช้าไป

**ขั้นตอน:**
1. เริ่มที่ `K_P = 0.50` (`K_I` และ `K_D` เป็น 0)
2. ลองวิ่งตรงยาวๆ ดูว่าหุ่นกลับมาตรงเองไหม
3. ถ้ายังเบี้ยวอยู่ → เพิ่มทีละ **0.5** (0.5 → 1.0 → 1.5 → 2.0)
4. ถ้าหุ่นเริ่ม**ส่ายซ้ายขวา** = แรงไป ให้ถอยลงมา 1 ขั้น
5. อยากให้หายส่ายเร็วขึ้น → เติม `K_D` ทีละ `0.05`
6. ถ้ายังเบี้ยวค้างเป็นมุมเดิมไม่หาย (เช่นพื้นเอียง) → เติม `K_I` ทีละ `0.01` (อย่าเกิน 0.05)

ค่าที่ใช้ได้จริงส่วนใหญ่อยู่แถว **1.0 – 3.0**

## 11. Checklist ทดสอบก่อนลงสนาม

ทำตามลำดับ **ห้ามข้าม** โดยเฉพาะข้อ 2

### ☐ 1. เซนเซอร์ติดต่อได้

เปิด Serial Monitor ของ Master ต้องเห็น:
```
BNO085 READY
```
ถ้าเห็น `ERROR: BNO085 NOT FOUND` → ไปดู [หัวข้อ 12](#12-แก้ปัญหาที่เจอบ่อย)

### ☐ 2. ⚠️ ทิศทางของ Yaw ถูกต้อง (สำคัญที่สุด)

**ยกล้อลอยจากพื้น** แล้วดู `>Yaw_Global` ใน Teleplot ฝั่งบอร์ดล้อ

| หมุนตัวหุ่น | `Yaw_Global` ต้อง |
|---|---|
| **ทวนเข็มนาฬิกา** (ซ้าย) | **เพิ่มขึ้น** ⬆️ |
| **ตามเข็มนาฬิกา** (ขวา) | **ลดลง** ⬇️ |

**ถ้าได้ผลตรงกันข้าม = ติดตั้งเซนเซอร์กลับด้าน** 🚨
ห้ามขับต่อเด็ดขาด เพราะ Heading Assist จะดันหุ่นผิดทางแล้วหุ่นจะหมุนติ้ว
→ ต้องแก้การติดตั้งให้ถูกก่อน

### ☐ 3. คำสั่งรีเซ็ตทิศทำงาน

พิมพ์ **`R`** ที่ Serial Monitor ของ Master → ต้องขึ้น
```
BNO085 YAW RESET TO 0 DEG
```
และ `Yaw_Global` ต้องกลายเป็น 0

> ข้อนี้เช็คแค่ตอนทดสอบหน้าคอม ไม่จำเป็นต้องทำก่อนแข่ง
> เพราะ Heading Assist ใช้แค่ผลต่างของมุม ไม่สนว่า 0 อยู่ตรงไหน

### ☐ 4. Heading Assist ตอบสนอง (ยกล้อลอย)

สั่งวิ่งหน้าค้างไว้ แล้วบิดตัวหุ่นด้วยมือ
- `Head_Active` ต้องเป็น **1**
- `Head_Error` ต้องเปลี่ยนตามที่บิด
- `Head_Corr_RPM` ต้องมีค่าออกมา (ไม่ใช่ 0 ตลอด)

ถ้า `Head_Corr_RPM` เป็น 0 ตลอดทั้งที่ `Head_Error` ไม่ใช่ 0 → เช็คว่า `HEAD_K_P` ไม่ใช่ 0

### ☐ 5. gyro หลุดแล้วเด้งกลับถูก

**ถอดสาย I2C ของ BNO085 ตอนหุ่นทำงาน**
- Serial ของ Master ต้องขึ้น `GYRO LOST -> HEADING ASSIST DISABLED`
- `Gyro_Valid` ต้องกลายเป็น **0**
- หุ่นต้องยัง**บังคับได้ปกติ** (แค่ไม่มีตัวช่วยกันเบี้ยว)

### ☐ 6. สาย UART หลุดแล้วปลอดภัย

**ถอดสาย UART ระหว่าง Master กับบอร์ดล้อตอนวิ่ง**
- ล้อต้องหยุดภายใน **0.3 วินาที**
- เสียบกลับแล้ว**ต้องไม่กระชากออกตัว**

### ☐ 7. ทดสอบวิ่งจริง

1. กด **L2** (โหมด SuperSlow) แล้วลองวิ่งตรงก่อน — หุ่นต้องไม่เบี้ยว
2. ค่อยเพิ่มเป็น R2 (Slow) แล้วความเร็วปกติ
3. ลองหมุนหุ่น 90° แล้วดันจอยขึ้น → **หุ่นต้องวิ่งตามหัวตัวเอง** (Local Frame)
   ถ้าหุ่นวิ่งไปทิศเดิมของสนาม แปลว่าแฟลชเฟิร์มแวร์เก่าอยู่

| หุ่นหมุนติ้วเอง 🚨 | **ทิศ Heading Assist กลับด้าน** | ปิดหุ่นทันที แล้วเปลี่ยน `HEADING_ASSIST_DIR` เป็น `-1` |
| หุ่นส่ายซ้ายขวาตอนวิ่งตรง | `HEAD_K_P` แรงไป | ลด `HEAD_K_P` ลง แล้วเติม `HEAD_K_D` |
| หุ่นไม่ขยับเลยหลังแฟลช | **แฟลชไม่ครบทั้ง 2 บอร์ด** | แฟลช Master + Wheel ใหม่ทั้งคู่ |
| `Head_Corr_RPM` เป็น 0 ตลอด | `HEAD_K_P` เป็น 0 หรือ error ยังไม่เกิน deadband 1° | เช็คค่าใน `config_wheels.h` |

## 13. ข้อจำกัดที่ต้องรู้

1. **yaw ดริฟต์ได้** — เพราะใช้ Game Rotation Vector (ไม่ใช้เข็มทิศ)
   แต่ไม่ค่อยกระทบแล้ว เพราะ Heading Assist จับทิศใหม่ทุกครั้งที่เริ่มวิ่ง

2. **0 องศาไม่ใช่ทิศเหนือ** — แต่คือ "ทิศที่รีเซ็ตไว้ล่าสุด" (หรือทิศตอนบูต)

3. **IMU อยู่บอร์ด Master เท่านั้น** — บอร์ดล้อไม่มีเซนเซอร์ของตัวเอง
   ถ้าสาย UART หลุด บอร์ดล้อจะไม่รู้ทิศเลยและหยุดทำงานภายใน 300 ms

4. **yaw อัปเดตที่ 30 Hz** แต่ส่งข้ามบอร์ดที่ 50 Hz และลูปควบคุมวิ่งที่ 100 Hz
   → ค่า yaw ที่บอร์ดล้อเห็นจะเก่ากว่าความจริงประมาณ 33 ms
   ซึ่งเพียงพอสำหรับการแก้ทิศ แต่ไม่เหมาะกับการควบคุมที่ต้องการความไวสูงกว่านี้

5. **ใช้แค่ yaw** — roll/pitch คำนวณไว้แล้วแต่ยังไม่ได้เอาไปใช้กับอะไร
   (เผื่อในอนาคตอยากตรวจว่าหุ่นกำลังจะพลิกคว่ำ)

6. **Heading Assist ไม่ได้ช่วยตอนเลี้ยว** — ออกแบบมาให้ปิดตัวเองทันทีที่คนขับกดปุ่มเลี้ยว
   เพราะถ้าไม่ปิดจะกลายเป็นสู้กับคนขับ
